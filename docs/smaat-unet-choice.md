# Why SmaAt-UNet for "Will We Get Wet?"

The [README](../README.md) frames the question as a canoeing decision in Utrecht, but the starter only looks at rain that has already fallen at De Bilt, using one hourly station total. That is useful for a demonstration, but it cannot see a shower moving in from the southwest, and [BACKLOG.md](../BACKLOG.md) asks us to predict rain that will matter for the afternoon (step 3) and to show that we beat a simple baseline (step 4). A learned model that works on radar maps fits that brief much better, because radar shows where rain is now and how it is moving. SmaAt-UNet is a published, open-source model built for exactly this: predicting the next precipitation maps in the Netherlands from recent KNMI radar.

The idea is easy to picture. Each radar frame is an image of rain intensity over a region, updated every five minutes. SmaAt-UNet takes the last 12 frames (one hour) stacked as 12 input channels, and it predicts the radar map 6 frames (30 minutes) ahead. Internally, a U-Net encoder shrinks the image step by step to capture large patterns, such as the position of a rain band, and a decoder grows it back to full resolution, with skip connections that carry fine detail across. The "Small" and "Attention" parts keep the model light: depthwise-separable convolutions reduce the number of weights, and attention modules help it focus on the rainy areas. The paper reports performance comparable to larger models with about a quarter of the trainable parameters, which is why we think it can train on a 4 GB GPU with small batches. We have not measured memory use on that card yet.

Using it here means building our own dataset, because the authors share their training data only on request. The [repo's loader](https://github.com/HansBambel/SmaAt-UNet/blob/master/utils/dataset_precip.py) expects an HDF5 file with `train` and `test` groups that each hold an `images` array, so the practical route is to build that file from KNMI RTCOR-5m radar (CC-BY-4.0). That is backlog steps 1 and 2. For step 3, a sensible target is "rain of at least X mm in the radar pixel covering De Bilt or Utrecht within the next 30 minutes", which gives a yes/no answer for the canoeing decision. For step 4, the baseline stays "raining now, so rain next hour" from the backlog, and we can also compare against KNMI's own `radar_forecast 2.0` nowcast. Step 5 turns the predicted maps into a plain outlook, and step 6 has to be framed as a historical demonstration, as the README already says, not a live forecast.

There are limits to keep in mind. Deep models trained to minimise error produce smooth, blurred forecasts, and that hurts heavy-rain cases most, which matter for a canoe trip. A 30-minute horizon is short enough that blur is less of a problem, but we should still check the heavy-rain events and report them separately. The published results come from 2016–2019 data and a different software setup, and the repo's dependencies have changed since the paper, so our numbers will not reproduce exactly. We should report results honestly, including if the model does not beat persistence.
